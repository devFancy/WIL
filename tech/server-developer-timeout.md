# 서버 개발자가 알아야 할 타임아웃과 유형 알아보기

이 글은 서버 애플리케이션을 개발하고 운영하는 백엔드 개발자의 관점에서 작성되었다.

> 예상 독자

- 타임아웃에 대한 개념과 유형에 대해 궁금한 개발자

- 타임아웃 에러가 발생했을 때, 이것이 네트워크 문제인지 서버 로직 문제인지 헷갈리는 개발자

- Spring Boot 등을 이용해 외부 API 연동이나 DB 설정을 직접 다뤄야 하는 백엔드 개발자

## 타임아웃이란

타임아웃이란 클라이언트가 서버에 특정 작업을 요청했을 때,
정해진 시간 내에 작업이 완료되지 않으면 해당 작업을 강제로 중단(실패 처리)시키는 메커니즘을 말한다.

타임아웃은 왜 필요할까?

- 무한 대기 방지(Blocking Prevention): 서버의 응답이 없는 상태로 클라이언트 프로세스가 영원히 멈춰 있는 것을 막는다.
- 리소스 관리(Resource Management): 커넥션 풀(Connection Pool) 등의 한정된 자원이 특정 요청에 의해 계속 점유되는 것을 방지하여, 다른 요청들이 정상적으로 처리되도록 한다.
- 빠른 실패(Fail-Fast): 문제가 생겼을 때 빠르게 실패 처리를 하여 시스템 전체의 장애로 번지는 것을 막는다.

## 타임아웃 유형

주로 타임아웃은 통신의 단계(연결 시도, 데이터 수신, 데이터 송신)에 따라 세 가지로 구분된다.

### 1. Connection Timeout (연결 타임아웃)

클라이언트가 서버와 TCP 연결(3-Way Handshake)을 맺으려고 시도했으나, 정해진 시간 내에 연결이 성립되지 않는 경우에 발생한다.

주로 **네트워크나 인프라** 환경의 문제일 가능성이 높다.

- 발생 시점: 클라이언트가 `SYN` 패킷을 보낸 직후부터 카운팅이 시작된다.

- 발생 조건: 서버로부터 `SYN-ACK` 응답을 타임아웃 시간 내에 받지 못함.

- 주요 원인
    - 서버가 꺼져 있거나 비정상 상태 (Listen 불가).
    - 방화벽(Firewall)이 포트 접근을 차단하여 패킷이 드랍됨.
    - 네트워크 주소가 잘못됨.

### 2. Read Timeout (읽기 타임아웃)

클라이언트와 서버 간 연결은 성립되었으나, 데이터를 읽어오는 과정에서 일정 시간 동안 데이터 유입이 없으면 발생한다.
(`Socket Timeout`이라고도 부른다.)

주로 **서버 애플리케이션의 로직 처리 지연**이 원인인 경우가 많다.

- 핵심 원리
    - TCP 통신은 데이터를 한 번에 보내지 않고 패킷(Packet) 단위로 쪼개서 스트림(Stream) 형태로 보낸다.
    - Read Timeout은 전체 데이터를 다 받는 데 걸리는 시간이 아니라,
      **마지막으로 데이터를 받는 시점부터 다음 데이터를 받을 때까지의 대기 시간**을 의미한다. (패킷이 하나라도 도착하면 카운팅은 초기화된다.)

- 발생 시점: 클라이언트가 `InputStream.read()` 메서드를 호출하고 데이터를 기다리는 순간부터 카운팅이 시작된다.

- 발생 조건: 설정된 시간 내에 서버로부터 단 하나의 패킷(바이트)도 수신하지 못한 경우.

- 주요 원인
    - 서버의 로직 처리가 오래 걸려 첫 번째 데이터를 보내지 못하는 경우.
    - 클라이언트가 요청한 데이터의 양이 너무 많아 서버가 응답을 준비하는 데 시간이 걸리는 경우.
    - 네트워크 불안정으로 전송 중간에 패킷이 유실되어 데이터 흐름이 끊긴 경우.

- 참고 사례
    - 토스페이먼츠에서는 결제 처리와 관련된 API(자동결제 승인, 거래 조회, 정산 조회)의 Read Timeout 기본값을 60초로 넉넉하게 설정하고 있다.
    - 또한, 타임아웃 이후에 결제 승인과 같이 민감한 API가 중복 호출되는 것을 막기 위해,
      멱등키(Idempotency Key)를 사용하여 안전하게 재요청을 보낼 수 있도록 설계되어 있다.

### 3. Write Timeout (쓰기 타임아웃)

클라이언트가 서버로 데이터를 보낼 때(요청 전송), 일정 시간 내에 데이터 쓰기 작업을 완료하지 못하면 발생한다.

- 발생 시점: `OutputStream.write()`를 호출하여 데이터를 전송하는 동안 카운팅된다.

- 발생 조건: 설정된 시간 내에 데이터 전송 작업(패킷 송신 및 ACK 수신)이 완료되지 않은 경우.

- 주요 원인
    - 클라이언트가 전송하려는 데이터가 너무 큰 경우 (대용량 파일 업로드 등).
    - 서버가 데이터를 처리하거나 읽어가는 속도가 클라이언트의 전송 속도보다 현저히 느린 경우 (Back Pressure).
    - 네트워크 대역폭 제한으로 전송 속도가 떨어진 경우.

## 타임아웃 유형을 표로 정리하면

정리한 Connection, Read, Write Timeout의 차이를 표로 비교하면 다음과 같다. (from Gemini 3 Pro)

| 구분      | Connection Timeout                          | Read Timeout                                 | Write Timeout                         |
|:--------|:--------------------------------------------|:---------------------------------------------|:--------------------------------------|
| 개념      | 서버와 연결(Handshake) 자체가<br>성립되지 않음            | 연결은 됐으나,<br>데이터 수신이 멈춤                       | 서버로 데이터를 보내는 작업이<br>시간 내에 안 끝남        |
| 카운팅 기준  | 연결 시도 직후<br>(SYN 패킷 전송)                     | 데이터 대기 시작<br>(read() 호출)                     | 데이터 전송 시작<br>(write() 호출)             |
| 카운팅 초기화 | 해당 없음<br>(연결 성공 시 종료)                       | 패킷(데이터) 수신 시마다<br>즉시 초기화 (중요)                | 해당 없음<br>(전송 완료 시 종료)                 |
| 주요 원인   | [네트워크/인프라]<br>서버 다운, 방화벽 차단,<br>잘못된 IP/Port | [서버 로직/앱]<br>Slow Query, 스레드 고갈,<br>중간 패킷 유실 | [데이터/전송환경]<br>대용량 업로드,<br>서버 수신 속도 저하 |
