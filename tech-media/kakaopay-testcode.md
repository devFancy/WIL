## 문제 상황과 해결 과정 (Mock Server -> @MockBean -> @TestConfiguration)

외부 서버와 연동하는 과정에서 테스트코드 작성시 Mock Server를 사용했음.

하지만 의존 관계가 복잡해지면, 외부 서버를 의존하는 모든 구간의 Mock Server 코드를 수정해야 하는 번거로움이 발생함.

이를 해결하기 위해 `@MockBean`을 도입함.

`@MockBean`은 행위 자체를 Mocking 하여 주입하므로 문제가 간편하게 해결되는 듯했다.

하지만, 여기서 치명적인 성능 문제가 발생했음.

`@MockBean` 을 사용하면 스프링의 Application Context가 오염(Dirty)된 것으로 간주되어, 테스트마다 컨텍스트 초기화가 반복됨.

`@MockBean`이 늘어날수록 초기화 시간도 비례해서 늘어나므로, 결국 빌드 성능에 악영향을 줌.

멀티 모듈 및 다양한 환경을 고려했을 때, 해당 어노테이션을 사용하지 않기로 결정함.

대안으로 `@TestConfiguration`을 활용하여 Application Context 초기화 문제를 해결함. (단, 이 구조의 필요성은 싱글 모듈보다 멀티 모듈 환경에서 훨씬 높음)

가짜 객체(Stub)를 실제 Bean으로 등록하고 생성자 주입으로 대체하여 Context 재사용성을 확보함.

## 멀티 모듈 환경에서의 구조적 개선 (java-test-fixtures)

위 방식을 적용하니, 멀티 모듈 환경에서 HTTP Client 모듈을 참조하는 과정에서 의존성 문제로 인해 중복 코드가 발생하는 부작용이 생김.

이를 해결하고자 `java-test-fixtures` 플러그인을 도입함.

이를 통해 멀티 모듈 환경에서도 테스트 의존성(Fixtures 등)을 공유할 수 있게 되어 문제를 해결함.

## 운영 코드와 테스트 코드의 분리 철학

java-test-fixtures 사용 시 main 디렉터리에서 test 의존성에 접근 가능하다는 구조적 딜레마가 생김.
"테스트를 쉽게 하기 위해, 운영 코드 설계를 변경하는 것이 옳은가?"

-> 바람직하지 않음.

테스트 의존성을 실제 구현 코드 영역과 명확하게 분리하는 것이, 비록 과정이 복잡하고 불편해 보여도 충분한 가치가 있다고 생각함.

## 테스트 불가능 영역(Black Box)을 대하는 자세

테스트할 수 없는 영역에 대한 관점이 중요함.

테스트 코드 작성이 불가능한 이유는 다양하며, 이런 영역을 `Black Box`라 칭함.

가장 큰 문제는 이 영역의 의존성이 직/간접적으로 연관된 모든 구간에 전이된다는 점임.

따라서 의존성이 전이되지 않도록 격리하는 것이 핵심임.

즉, Black Box 영역 자체는 테스트하지 못하더라도, 다른 객체들은 여전히 독립적으로 테스트를 진행할 수 있는 환경을 구성해야 함.

# [실무에서 적용하는 테스트 코드 작성 방법과 노하우 Part 2: 테스트 코드로부터 피드백 받기](https://tech.kakaopay.com/post/mock-test-code-part-2/)

> 발행 날짜: 2023.08.28

테스트 코드는 '**구현 코드의 첫 사용자**'로서 다양한 피드백을 제공한다. 해당 피드백을 반영하면 구현 코드를 좋은 코드 디자인으로 자연스럽게 개선할 수 있다.

결국 테스트 코드를 적극적으로 반영하는 과정에서 자연스럽게 더 나은 구현 코드를 작성하는 선순환 구조가 형성된다는 점이다.

이렇듯 테스트 코드는 구현 코드와 긴밀하게 상호작용하며 소통하는 중요한 코드다.

## 객체의 책임 분리

중요한 점은 해당 객체가 가지고 있는 책임은 크게 두 가지로 분리되는데,

첫 번째는 비즈니스 로직이고, 두 번째는 HTTP 통신을 담당하는 로직이다.

이렇게 책임을 분리하는 이유는 소프트웨어의 변화에 맞게 대응하는 것이 상대적으로 쉽기 때문이다.

어떠한 변경이 발생했을 때 영향을 최소화하기 위해 객체에 대한 역할과 책임이 적절하게 분리되어 변경에 대비해야 한다.

이런 작업은 테스트 코드를 통해 원활히 할 수 있다.

## 객체에 대한 책임을 분리해야 주요 관심사를 테스트하기 쉬워진다.

책임 분리의 중요성을 알지만, 실천은 어렵다.

하지만 테스트 코드를 작성하다보면 구현이 적절하지 않다는 신호를 받게 된다.

- 주요 관심사가 아닌 부분에 너무 많이 관여하고 있다고 느껴진다면, 실제 구현 코드가 잘못되었을 가능성이 높다.
- 테스트하고자 하는 주요 관심사를 검증하기 어렵다면, 이 또한 테스트 코드가 주는 설계 개선 피드백이다.

따라서 객체의 책임과 역할을 명확히 하면, 자연스럽게 객체가 분리된다.

이때 분리된 객체의 주요 관심사를 테스트하기 위해 Mock Server를 활용하게 된다.

- Mock Server 테스트에는 의도대로 요청 분문이 직렬화되었는지, 응답 본문이 역직렬화되었는지, 필수 헤더 정보 등이 올바르게 전송되었는지 검증을 진행한다.

## 객체는 본인의 책임을 다해야 한다. 그래야 전이가 발생하지 않는다.

작업이 A -> B -> C 순서의 컨베이어 벨트 처럼 진행된다고 할 때,

만약 객체 A가 자신의 책임을 다하지 않으면, 그 책임이 B에게 가고, B는 이후의 C에게 책임을 떠넘기게 된다.

이는 전체 시스템에 부정적인 영향을 준다.

따라서 테스트 코드가 주는 피드백을 활용해서 각 객체에 적절한 책임을 할당하고, 본연의 주요 관심사에 집중하도록 해야 한다.

## 외부 의존성 전파 문제 개선

HTTP 통신을 담당하는 HTTP Client 모듈은 특성상 다른 모듈에서 자주 사용된다.

이때 HTTP Client 모듈에서 RestTemplate 와 같이 특정 외부 라이브러리의 객체를 그대로 반환하면,

해당 라이브러리에 대한 의존도가 모듈 전체로 퍼지게 된다.

즉, 라이브러리가 변경될 때 이를 의존하는 모든 외부 모듈에 영향(변경)을 주게 되어 결합도가 높아진다.

이를 해결하기 위해 외부 영향을 최소화할 수 있도록 HTTP Client 모듈 내부에서 제어권을 가져야 한다.

- 기존에 `ResponseEntity<T>` 객체로 반환(라이브러리 종속 객체)했다면,
- 반환 타입을 `Pair<Int, T?>` 와 같이 (독자적인) 객체 타입으로 반환한다. -> `Pair<Int, T?>` 객체의 타입으로 반환할 때 내부 모듈에서 사용할 `HTTP Status Code`를 직접
  정의해서 반환한다.

이렇게 내부 모듈에서 사용할 HTTP Status Code 등을 포함한 독자적인 객체로 변환하여 반환하면, 외부 라이브러리가 변경되더라도 이를 사용하는 외부 모듈에는 영향이 가지 않는다.

## 다양하고 복잡한 케이스에 대한 개선

주문 서비스에서 주문을 등록할 때 다양한 인프라계층에 저장된 정보를 조회해야 하는 상황이고

다양한 관심사와 복잡한 로직으로 이루어져 있다고 가정했을 때, 테스트 코드를 작성하기가 어려워질 것이다.

특히 Given 절에 대한 설정하는 것 자체가 큰 부담이 된다.

이렇게 테스트 코드 작성이 어렵다고 느껴질 경우에는 무작정 테스트 코드를 작성하는 것이 아니라, **객체 디자인을 다시 한번 고민해야 한다**는 걸 명심하자.

고민하다 보면, 주문 서비스(OrderService) 에서 너무 많은 책임과 역할이 집중되었다는 걸 느끼게 된다.

이렇게 특정 객체에 책임이 과하게 집중되어 있을 경우, 해결 방안은 **협력 관계에 참여할 새로운 객체를 추가하여 책임을 분산**시키는 것이다.

주문 서비스에는 두 가지 주요 책임이 존재한다.

- 각기 다른 인프라 데이터 조회
- 복잡한 주문 로직 처리 -> OrderServiceSupport 객체로 분리

이렇게 책임을 분리하면 복잡한 주문 로직을 테스트할 때 인프라 설정 없이 순수 POJO 구조로 간단하게 테스트할 수 있다.

이는 추후 인프라 계층이 변경되더라도 핵심 비즈니스 로직은 영향을 덜 받게 해 준다.

## 마무리하며

객체 및 모듈간의 의존성을 분리하고 객체의 역할과 책임을 적절하게 할당하는 것은 이미 아는 사실이지만, 이를 실제로 적용하는 과정은 어려울 수 있다.

테스트 코드는 안정성, 문서화뿐만 아니라, **설계에 대한 피드백**이라는 중요한 가치를 제공한다.

구현 코드와 테스트 코드 간의 피드백을 주고받으면서 지속적으로 리팩터링을 수행한다면,

주요 관심사를 지키면서도 코드 품질을 자연스럽게 높일 수 있을 것이다.

# [실무에서 적용하는 테스트 코드 작성 방법과 노하우 Part 3-1: Given 지옥에서 벗어나기 - 객체 기반 데이터 셋업의 한계](https://tech.kakaopay.com/post/given-test-code/)

> 발행 날짜: 2024.08.14

Given 단계는 테스트 준비 단계로 복잡한 데이터 셋업이 자주 요구된다.

주문 시스템이 상품, 회원, 쿠폰, 결제 등 여러 요소가 결합된 복잡한 구조로 이루어져 있을 경우,

각 요소들이 상호작용하여 테스트 시나리오가 만들어지는데, 이때 모든 경우를 테스트하기 위해 서로 다른 데이터 셋업이 필수적이다.

이 과정은 번거롭고 시간이 많이 소요되며, 특히 객체 기반으로 데이터 셋업을 할 때 객체 간의 의존성을 직접 설정해야 하기 때문에, 어려움이 더 커지게 된다.

이러한 환경을 극복하기 위해 복잡한 데이터 셋업을 어떻게 효과적으로 관리할 수 있는지에 대한 전략과 실무에서 활용할 수 있는 팁을 공유하고자 한다.

## 요청 데이터를 JSON 파일 기반으로 데이터 셋업한다.

객체 기반의 데이터 셋업할 때 아래와 같이 다양한 요구사항이 들어온다면, 테스트하기 어려워지게 된다.

- 복잡한 객체 구조 설정 -> 리스트 기반의 필드가 추가될 경우, 중첩된 리스트 구조(e.g. tags)가 추가될 경우
- 데이터 포맷 일관성 유지의 어려움
- 유효하지 않은 데이터 테스트의 제약 -> Enum 타입의 status 필드는 정의되지 않은 값을 테스트하기 어려운 환경을 만든다.
    - -> 이는 비정상적인 데이터 입력 시나리오를 검증하려면 불필요한 예외 처리 로직이 추가되어야 한다.

이를 해결하기 위한 방안으로 테스트의 주요 관심사를 분리한 뒤에, JSON 파일을 이용해서 데이터 셋업을 고려해볼 수 있다.

- 요청 데이터를 JSON 파일로 관리한다. -> 객체 기반 설정의 복잡성 줄이고, 코드의 가독성과 유지보수성을 높일 수 있다.

## 특정 상태의 데이터 셋업이 필요할 경우 -> SQL 어노테이션을 활용한다.

테스트 코드를 작성할 때 특정 시점의 데이터를 설정해야 하는 경우, `@Sql` 기반 데이터 셋업을 활용한다.

- 해당 어노테이션은 테스트 실행 전에 지정된 SQL 파일을 실행하여 **데이터베이스 상태를 원하는 대로 셋업**해준다.
- SQL 파일로 필요한 상태로 설정 할 수 있기 때문에, 테스트의 핵심 기능 검증에 집중할 수 있다.

이를 통해 테스트 코드의 복잡도를 줄이고 효율성을 높일 수 있다.

## 복잡한 데이터 연관관계 설정이 필요한 경우 -> @SqlGroup 어노테이션을 활용한다.

`@SqlGroup` 어노테이션을 사용해서 복잡한 데이터 셋업을 관리할 수 있다.

- `*.sql` 파일을 통해 스키마를 설정한다.
- 이후 FK(외래 키) 관계를 가진 데이터를 설정한다.
- 또한, 테스트가 끝난 이후에 데이터를 삭제하는 쿼리를 작성해서 테스트 환경을 초기 상태로 되돌리는 방법도 있다.
- 이를 통해 데이터 셋업뿐 아니라, 정리 과정을 관리할 수 있다.

특히, **다양한 데이터를 애그리게이션하여 데이터를 가공하는 배치 애플리케이션**의 테스트 코드에서 이러한 방식이 적합하다.

- 복잡한 데이터 변환과 집계 작업을 손쉽게 검증할 수 있다.
- 여러 단계의 데이터 셋업과 정리가 필요한 경우에도 `@SqlGroup` 을 통해 테스트 환경을 구축할 수 있다.

### .sql 파일의 장점을 요약하자면,

`.sql` 파일을 이용한 데이터 셋업은 다음과 같은 이점을 가진다.

- 비즈니스의 로직 변경과 무관하게 테스트 셋업을 수행할 수 있다. -> 필요한 동작에 집중할 수 있다.
- sql 스크립트를 통해 복잡한 데이터 시나리오를 빠르게 설정할 수 있다. -> 객체 생성을 반복적으로 안해도 된다.
- 데이터 준비와 테스트 검증을 분리하여 코드를 더 깔끔하고 유지보수하기 쉽게 만든다.
- 다양한 데이터의 애그리게이션이 필요한 경우, 데이터 셋업과 흐름을 효율적으로 관리할 수 있다.

## 마무리하며

sql 파일과 어노테이션을 이용한 방법 외에 다양한 해결책이 존재할 수 있다.

중요한 점은 상황에 맞게 효율적인 방법을 찾아 적용하는 것이다.

# [실무에서 적용하는 테스트 코드 작성 방법과 노하우 Part 3-2: Given 지옥에서 벗어나기 - 스노우볼을 굴려라](https://tech.kakaopay.com/post/given-test-code-2/)

> 발행 날짜: 2025.02.26

스노우 볼처럼 작은 단위의 테스트 코드를 꾸준히 작성하고 재활용하면서 점진적으로 더 큰 로직의 테스트를 구성해 나가는 것이 중요하다.

이번 글에서는 Given 절의 재사용성과 모듈 간 공유를 극대화함으로써 복잡하고 반복되는 셋업 코드를 단순화하는 방법을 공유하고자 한다.

## Given 지옥

Given 절을 작성할 때 다양한 데이터를 셋업하다 보면, 정작 테스트하고자 하는 핵심 기능에 집중하는 시간보다 준비 시간이 더 오래 걸리는 주객전도가 발생한다.

이로 인해 의무감에 의한 최소한의 케이스만 작성되기 쉽다.

또한 Given 절을 재활용하지 않으면 동일한 셋업 코드가 많아져서 테스트의 핵심 관심사와 무관한 코드들의 양이 점차적으로 증가하게 된다.

예를 들어 특정 기능을 테스트할 때, 주요 관심사가 아닌 필드들까지 일일이 채워 넣어야 한다면

코드량이 비대해지고 **테스트의 핵심 의도를 파악하기 어려워진다.**

### 1. 파라미터 지옥

기존 테이블(엔티티)에 새로운 파라미터가 추가될 경우, 이 객체를 사용하는 모든 테스트 코드를 수정해야 한다.

작성해 둔 테스트 코드가 많을수록 유지보수 비용이 눈덩이처럼 불어나는 문제다.

이를 `파라미터 지옥`이라 부른다.

### 2. 멀티 모듈 환경에서의 테스트 코드 재사용 지옥

이러한 문제를 해결하기 위해 각 테스트마다 반복되는 부분을 **헬퍼 함수**로 추출하여 활용할 수 있다.

이렇게 하면 개별 테스트마다 복잡한 파라미터를 일일이 입력할 필요가 없어진다.

하지만 Gradle 멀티 모듈 프로젝트에서는 기본적으로 한 모듈의 테스트 코드를 다른 모듈에서 참조할 수 없다.

결국 동일한 데이터를 생성하기 위한 헬퍼 코드나 Given 코드를 각 모듈마다 중복해서 작성해야 한다.

이를  `멀티 모듈 환경에서의 테스트 코드 재사용 지옥`이라 부른다.

### 3. 외부 인프라 의존으로 인한 Mocking 지옥

예를 들어, '담당자에게 이메일을 전송'하는 기능이 추가되었다고 가정하자.

이 경우 HTTP 통신을 통해 외부로 알림 메일 전송 요청을 보내야 한다.

이때 요청을 위한 새로운 데이터 클래스를 추가하게 되는데, 이는 기존 클래스의 필드 구성과 거의 유사할 가능성이 높다.

문제는 이처럼 테스트 코드를 작성할 때, 핵심 비즈니스 로직이 아닌 **Mocking을 위한 부수적인 코드와 데이터 클래스가 많아지면서 테스트 코드가 지나치게 복잡해진다**는 점이다.

이를 `외부 인프라 의존으로 인한 Mocking 지옥`이라 부른다.

## Given 지옥으로부터 벗어나기

앞서 언급한 문제점들을 해결하기 위해 다음과 같은 전략을 사용한다.

- `DomainFixtures` 와 `DomainIoFixture` 를 통해 공통된 테스트 데이터를 헬퍼 객체로 만들어 재활용한다.
- `java-test-fixtures` 라이브러리를 Gradle 플러그인을 활용하여 모듈 간에도 테스트 전용 코드를 공유하도록 한다.

이 두 가지를 적용하면 불필요한 반복 작업과 복잡한 셋업 과정을 획기적으로 줄일 수 있다.

결과적으로 개발자는 테스트의 핵심 로직에만 집중할 수 있게 되며,
테스트 커버리지와 시스템 신뢰성을 효과적으로 향상시킬 수 있다.

- 참고: java-test-fixtures 라이브러리 관련해서 의존성 제공에 대한 자세한
  내용은 [실무에서 적용하는 테스트 코드 작성 방법과 노하우 Part 1: 효율적인 Mock Test](https://tech.kakaopay.com/post/mock-test-code/)을 참고하자.

## 마무리하며

테스트 코드는 작성할 때마다 본인 스스로 '도움이 되고 이득이다'라는 걸 느낄 수 있어야 지속 가능하다고 본다.

실무에서 복잡한 비즈니스 로직에 대한 테스트 코드를 작성하는 것이 결코 쉽지 않다.

하지만 한 번 작성한 것을 토대로 이후의 새로운 테스트 케이스를 쉽게 만들 수 있게 된다면,

이는 테스트 작성을 지속할 수 있는 강한 원동력이 된다.

우선 작은 단위의 기능에 대한 테스트를 작성해보자.

그리고 Given 절을 재활용해 더 큰 로직의 테스트를 구성해나가면 점차적으로 쉬워질 것이다.

이러한 전략을 토대로 꾸준히 적용하다보면 테스트 코드 작성이 점점 더 수월해질 것이고,
코드 품질은 자연스럽게 향상될 것이다.
