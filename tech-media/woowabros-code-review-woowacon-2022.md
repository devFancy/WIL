## 코드리뷰, 왜 해야할까?

이론적인 얘기

- 잠재적인 버그와 성능 이슈를 제거해 코드를 진정시킨다.
- 코드가 잘 생겨지고 미래에 손이 덜 간다.
- 서로 지식을 공유하며 함께 성장할 수 있다.
- 앞으로 코딩하는데 자신감이 생기고 즐거워진다.

우아한형제들의 코드 리뷰를 적용한 경험을 바탕으로 정리하면 이유는 아래와 같다.

- 코드의 일관성 유지
    - 팀내 코딩 스타일을 정착시켜야 이후에 일관성이 유지된다고 봄.
- 로직의 더블 체크
    - 빠듯한 일정과 잦은 실수를 방지하기 위해 더블 체크를 통해 안정성을 확보함.
    - (궁금증) 빠뜻한 일정인데, 더블 체크를 할 시간과 여유가 있는가? 발표에 대한 논리적인 흐름이 구체적이지 않아서 아쉬웠음.
- 중복 제거
    - 중복된 부분을 파악하고 통일하거나 추상화함.
    - 통일한 사례) 날짜와 가격을 계산하는 로직을 통일함. (Util, Hook)
- 함께 성장
    - 작업하면서 마주한 이슈와 지식과 더불어,
    - 성능, 유지보수 관점에서 더 좋은 접근법에 대한 고민과 공유함.

우리팀은 아래와 같은 순서로 진행한다.

- 코드 작성 -> 랜덤 리뷰어 배정 -> 리뷰 -> 어프로브 -> 자동 머지

특히, 우리팀만의 가진 특징은 아래와 같다.

- 프론트엔드 매니저
    - 코드 리뷰를 도와주는 전담 매니저(봇)이 있다.
    - 가끔 업무가 바쁠 경우, 봇이 슬랙 맨션으로 리뷰어에게 알림을 준다. e.g. @마xx(배민스토어웹플론트개발팀)이(가) 워크스페이스에 프론트엔드 매니저를 추가했습니다.
    - 알림 뿐만 아니라 자체 코드 리뷰, 자동 머지, 빌드 및 배포 자동화 작업까지 해주고 있다.
- 코어 코드리뷰 시간
    - 업무의 효율을 높여준, **오전**에 코어 코드 리뷰 시간을 준다.
- 자유로운 분위기 속 코드 리뷰
    - 캐주얼한 코멘트를 주고 받음 -> 불필요한 부분이라 부분이라고 생각할텐데, 이런 부분이 팀의 편한 분위기 속에서 자신의 이야기를 말할 수 있다고 본다.
    - 편한 분위기가 형성되어있다 보니, 격식을 차리는데 따로 리소스를 쓰지 않아도 된다.

코드리뷰 과정 속에서 크고작은 이슈들을 개선하면서 추가적으로 적용한 규칙은 아래와 같다.

- Approve 해주세요 대신 '리뷰해주세요'라고 말하기.
- MR 제목 규칙 정하기
    - 가독성 향상을 위해 규칙을 명시화함. e.g. {feat/refactor/fix 등}: {작업 내용} {JIRA 티켓명}
- 리뷰어를 배려한 MR 내용 작성하기
    - MR 작성할 때 작성하는 템플릿을 보완하기
    - 목적:
        - `리뷰어`는 MR만 보고 해당 내용을 빠르게 이해하고 파악하는 것
        - `작성자`는 MR 크기를 스스로 확인해서 범위를 조절하는 능력을 키우는 것
    - 부득이하게 작은 단위의 MR을 생성할 수 없는 경우에는 커밋 단위로 작업 내용을 설명하고 리뷰를 요청하고 있음.
- 히스토리 남기기

코드리뷰를 통해 배운 점은 아래와 같다.

- 리뷰어의 입장을 배려하는 자세와 규칙을 만드는 프로세스를 경험했다.
- 서로의 개발 경험과 지식을 공유하여, **퀄리티 높고 유지보수성이 뛰어난 로직을 개발하는 역량**을 키울 수 있다.
- 자유롭고 개방적인 분위기 속 지식 공유를 통해, 협업과 성장에는 **열린 분위기**가 중요하다는 것을 배웠다.
- 제품에 더 좋은 방향성이 보인다면 **기획자(PM)분께 먼저 제안**해보는 경험을 통해 기획자와 커뮤니케이션하는 스킬을 배웠다.
- 당장 구현해야할 기능 또는 할 일에 집중하고, 부가적인 리팩토링 등은 **후속 작업으로 분류**한다는 것을 배웠다. -> 우선순위 잘 세우기.
- (신입/주니어일 경우) 코드리뷰를 할 때 **용기내는 방법**을 배웠다. -> 모르는 것을 많이 물어보는 것은 신입의 특권은 농담 반, 진담 반처럼 말이다.

더 좋은 코드문화를 만들기 위해 제안한 점은 아래와 같다.

- 리뷰의 중요도 표시하기
    - 이모지를 활용하기 -> 🚨
- 사후리뷰 프로세스 적용하기
    - 긴급하게 코드를 수정하고 배포하는 경우
- 좋은 리뷰 공유하기
  - 회고 시간에 "이번주 BEST 코드리뷰를 공유하기"
  - 저장소에서 **라벨**을 활용해서 이번주 코드리뷰 표시하기 (e.g. 라벨: `이번주 리뷰`)

## Review

최근 회사에서 내가 작업한 부분에 대해 리뷰어와 코드리뷰를 하는 시간을 가지고 있다.
하지만 이보다 더 나은 코드리뷰를 위해 어떤 부분을 우리 회사에 맞게 적용해나갈 수 있을지 궁금해서 해당 영상을 보고, 나름 정리했다. (추후 다시 확인하기 위해)

영상이 32분이고, 기록하느라 거의 1시간 30분 정도 걸렸지만 그 시간이 아깝지 않을 정도로 생각보다 얻은 인사이트가 많았다.
그 중에서 코드리뷰 매니저(봇)을 활용하는 방법, 코드리뷰를 오전에 갖는 규칙, 그리고 좋은 리뷰를 공유하는 부분이 인상 깊었다.

코드리뷰를 하면서 배운 점들 중에서 "제품에 더 좋은 방향성이 보인다면 기획자분께 먼저 제안"하는 부분에 대해서 많은 공감됐다.
실제로 피드백 때 그러한 평가를 받았고, 이후에 기획자에게 먼저 제안해보는 경험도 가졌다.

개인적으로 중요하게 생각하는 건, 
코드리뷰를 해야하는 이유는 결국 더 나은 코드와 팀원들과 함께 성장한다는 점이라는 두 가지로 귀결된다는 점이다.
